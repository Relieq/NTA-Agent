# Battle Simulator (headless engine reuse) — Design

Date: 2026-09-11
Status: Approved (brainstorming) → ready for implementation plan
Owner: NTA-Agent execution/predictors

## 1. Problem

The current occupy/attack decision uses `BattlePredictor.from_stats` — a scalar
power proxy (`hp * attack` per pawn, army-value ratio, 1.5x margin). It is a
*conservative filter* ("is this fight clearly winnable"), not a *predictor*
("win/lose + how many pawns lost"). It ignores everything that actually decides
a battle in this game: unit-type restraint, per-fighter behavior/targeting,
grid positions, attack range, skills, buffs, heroes, towers, RNG.

Investigation of the decrypted client (`tools/re/decrypted/index.js`) showed the
combat engine is **not** a closed-form turn engine. It is a deterministic,
grid-based tactical auto-battler:

- `FSPModel` — lockstep frame loop (FPS). The in-game "forecast" runs this *same*
  engine headless (`battleLocalBegin({forecast:true})`) frame-by-frame until one
  side has no living owner pawns, then reports `isWin` + `lossLv`.
- `FSPBattleController` — orchestrates fighters, camps, RNG, buffs, strategies.
- `Fighter` — behavior-tree driven (`blackboard`, `beginAction`,
  `CheckUseSkillAttack`), A* movement (`SearchPoint`/`SearchRange`).
- `getAttackDamage` (~200 lines) — base attack → type restraint
  (ATTACK_RESTRAIN / DEFENSE_RESTRAIN / RESTRAIN_BEAST) → ~40 strategy ids,
  ~15 buff types, skills (PENETRATE/TELSON/…), hero specials, environment buffs,
  per-round state, RNG rolls.
- `RandomObj` — a trivial seeded LCG: `seed = (9301*seed + 49297) % 233280`.

A faithful hand-port to Python would be thousands of lines and extremely fragile
against game updates. The chosen approach reuses the **real** engine code.

## 2. Chosen approach (decisions locked)

- **Fidelity: reuse the game's own battle JS, headless.** Load the decrypted
  battle modules in Node, stub the minimum Cocos surface, rebuild the
  `area/gameHpr/mapHelper` object graph enough to call `battleLocalBegin` in
  forecast mode, step frames to settle, read the result. No formula porting.
- **Bridge: a persistent Node sidecar** speaking JSON-RPC over stdio. One warm
  process; Python calls it. Chosen over one-shot subprocess (startup cost) and
  in-process JS embedding (harder to load the large bundle + shims).
- **Determinism: single run with the client's exact seed.** The client forecast
  uses `randSeed = floor(playerUid/100) + area.index` and (per user observation)
  is reliable / worst-case-leaning. We reproduce that exact seed → the predictor
  matches the in-game forecast 1:1. No Monte-Carlo.

### What we do NOT need to supply (engine derives it)

Confirmed in the decrypted client:

- **Attack direction / entry**: computed from map geometry —
  `getAddArmyDir(attackerCellIndex, targetCellIndex)` → `passPoints[dir]`, with
  `passPoints = mapHelper.getPassPoints(areaSize)`. We have all inputs.
- **Enemy in-battle positions**: generated by
  `gameHpr.getAreaPawnConfInfo(cellIndex, landId, selfToCellDistance)`, which
  returns defenders already carrying `.point`. Positions are a deterministic
  function of land type + distance, not observed data.
- **Our pawn positions**: assigned by `toPawnsStrip(pawns, cellIndex, passPoint)`.
- **Turn order**: `Fighter.attackIndex`, from sorting by `attack_speed` (in
  `pawnBase`) then distance: `100*attack_speed + (99 - distance)`.

So marshaling supplies only data we already hold: our armies (pawns with
`id/lv/uid/buffs/skills/hero/treasures`), the target cell index + landId, our
distance to it, area size, and `playerUid`. Combat stats (`attack/hp/
attack_range`) come from `pawnAttr` (keyed `id*1000+lv`); the engine reads all
tables via `assetsMgr.getJsonData(table, id)`.

## 3. Architecture

Three units, each independently understandable and testable.

### 3.1 Node harness — `tools/battlesim/` (JS)

Purpose: run the real battle engine headless and answer `forecast` requests.

- `cc-shim.js` — minimal `cc` global the battle path touches: `_RF.push/pop`,
  `v2`/`Vec2` (with the vector ops used — `set2`, `sub`, `add`, …), `log`,
  `Enum`. Built up iteratively, driven by real "missing symbol" errors.
- `bundle.js` — evaluate the decrypted `index.js` module registry
  (`window.__require({Name:[fn,deps]})`), expose `__require`, and `require`
  the battle modules by name (`FSPBattleController`, `FSPModel`, `Fighter`,
  `BehaviorTree`, `StrategyObj`, `BuffObj`, `RandomObj`, `Tower`, `MainDoor`,
  `SearchPoint`, `SearchRange`, and their transitive deps).
- `assets.js` — `assetsMgr.getJsonData(table, id)` backed by
  `nta_agent/data/config/*.json`; plus a `gameHpr`/`mapHelper` stub that reuses
  the bundle's own generators (`getAreaPawnConfInfo`, `getPassPoints`,
  `getAddArmyDir`, `getBattlePoints`) where present, and provides the few
  player-context accessors the forecast path calls (`getUid`, `getPlayerInfo`,
  distances).
- `area-factory.js` — construct the `area` object (`init({index, owner, hp,
  cityId, armys})`), our army strip via `toArmyStrip`, enemy via
  `getEnemyArmys`, from a forecast input. **Highest-risk unit** (depth of the
  object graph).
- `forecast.js` — `forecast(input)`: build inputs, set `randSeed` from the
  client formula, `battleLocalBegin({camp:1, forecast:true, randSeed, fps,
  fighters, mul})`, drive `fspModel.update()` until settle (reuse the engine's
  own `onPlaybackEnd`/`settleResult`/`onComplete`), return
  `{isWin, lossLv, lossPercent, timeMs, survivors:{self:{alive,total},
  enemy:{alive,total}}}`.
- `server.js` — stdio JSON-RPC loop. Methods: `forecast(input)` and `ping`.
  One request → one deterministic result.

### 3.2 Python bridge — `nta_agent/execution/predictors/sim_bridge.py`

- Manages the Node sidecar: lazy spawn (`node tools/battlesim/server.js`),
  newline-delimited JSON-RPC over stdio, per-call timeout, restart on crash.
- `available()` → bool (node present + engine boots + `ping` ok).
- `forecast(input: dict) -> dict` or raises `SimUnavailable`.
- Lifecycle: process-wide singleton; closed on interpreter exit.

### 3.3 Python predictor — `nta_agent/execution/predictors/sim_predictor.py`

- `SimBattlePredictor` keeps the existing predictor interface:
  `predict(my_pawns, enemy_pawns) -> BattlePrediction` and a `pawn_power`
  attribute (delegated to the combat-stats valuer for army *selection* — sim is
  only for the final go/no-go).
- Builds the forecast input from `GameState` + the target: our selected
  army(ies) (pawns with `id/lv/uid/buffs/skills/hero/treasures`), target cell
  index, landId, distance, area size, `playerUid`.
- Calls `sim_bridge.forecast(...)`, maps the result into `BattlePrediction`:
  `win = isWin`, `loss_percent = lossPercent`, `loss_lv = lossLv`. Existing
  fields (`my_power`, `enemy_power`, `ratio`) are filled from the stats valuer
  for continuity; they no longer drive the decision.

### 3.4 Integration & fallback

- `Actions.predict_occupy` and `OccupyCell` prefer `SimBattlePredictor` when
  `sim_bridge.available()`; otherwise fall back to `BattlePredictor.from_stats`.
- A sidecar crash/timeout during a tick → catch, mark unavailable for this tick,
  fall back to the stats predictor, log; retry the sidecar next tick.
- The autonomous loop must never die because the simulator is missing or fails.

## 4. Data flow

```
OccupyCell.applies
  → discover candidates (adjacent, occupiable)
  → pick strongest reachable army (stats pawn_power)
  → SimBattlePredictor.predict(army.pawns, candidate.defenders, target=cell)
      → build forecast input (uid, cell, landId, distance, areaSize, armies)
      → sim_bridge.forecast(input)  ── stdio JSON-RPC ──▶ Node server.js
            → area-factory builds area+fighters
            → forecast.js: battleLocalBegin(forecast, seed) → step → settle
            → {isWin, lossLv, lossPercent, survivors}
      ◀── BattlePrediction(win=isWin, loss_percent, loss_lv)
  → choose the safest winnable target → act: occupy_cell
```

## 5. Testing (TDD)

- **JS golden (deterministic):** a known matchup (our pawn `3101` lv1 vs npc
  `4101` lv1) at a fixed cell → snapshot `{isWin, lossLv, lossPercent}`. Locks
  the engine boot + determinism.
- **Accuracy proof (client parity):** capture the client's real forecast for one
  or more setups (via the running game, same seed) and assert the headless
  engine reproduces `isWin` and `lossLv` exactly. This is the correctness claim.
- **Python bridge unit:** against a fake sidecar (an echo script) — spawn,
  request/response framing, timeout, crash-restart, `available()` false path.
- **Marshaling unit:** `GameState` + target → forecast input dict, with recorded
  fixtures (no Node required).
- **Integration (`requires_node` mark):** real sidecar + real engine, one
  end-to-end `predict`.
- **Fallback:** with the sidecar forced unavailable, `predict_occupy` returns a
  stats-based prediction and the loop proceeds.

## 6. Phasing & gates

- **Phase 1 — feasibility gate (spike-like, but kept):** boot the engine in Node
  with the shim + bundle loader + minimal `area/gameHpr/mapHelper`, and run
  *one* battle to a real `{isWin, lossLv}`. If the `area/gameHpr` object graph
  proves too deep to reconstruct, **stop and regroup with the user** — do not
  silently fall back to a heuristic. This phase produces the JS golden test.
- **Phase 2 — sidecar + bridge:** `server.js` JSON-RPC + `sim_bridge.py` with its
  unit tests.
- **Phase 3 — predictor + marshaling:** `sim_predictor.py`, marshaling, mapping
  to `BattlePrediction`, unit + integration tests.
- **Phase 4 — integration + fallback:** wire into `predict_occupy`/`OccupyCell`,
  fallback path, live verification of the autonomous loop.

## 7. Risks

- **Object-graph depth (highest):** the forecast path may reach further into
  `gameHpr`/`world`/`player` than expected. Mitigation: Phase 1 gate; build the
  stub iteratively from real errors; reuse bundle generators rather than
  reimplement.
- **Node dependency:** new runtime requirement for the predictor only. The agent
  stays headless (no game client needed). Fallback keeps the loop alive if Node
  is absent.
- **Config drift / game updates:** re-extracting `index.js` + config tables is
  the maintenance path; the golden + parity tests catch divergence.
- **Sensitive artifacts:** the decrypted `index.js`, config tables, and the
  XXTEA key remain gitignored. The Node harness reads them at runtime by path;
  it must not embed or commit them. Add `tools/battlesim/` code (only) to git;
  keep any copied engine/config out.

## 8. Out of scope

- PvP-specific target selection strategy (brain layer).
- Auto-unlocking new pawn types (StudySelect) — separate concern.
- Replacing the stats `pawn_power` used for army *selection*; the sim decides
  go/no-go, selection stays cheap.
